# MIG Classroom

An online classroom / learning-management web app for a German-language
academy. Three roles: **students**, **teachers**, **admins**. Core domains:
assignments, marks, questions, exams.

The user (project owner) is still learning to code. Explain reasoning as you
go, don't skip steps, and avoid moving too fast when making changes.

## Tech stack (decided — do not change without asking)

- **Language:** TypeScript everywhere
- **Monorepo:** pnpm workspaces + Turborepo
- **Frontend:** Next.js (App Router) + Tailwind CSS + shadcn/ui
- **Backend / DB / auth / storage:** Supabase (Frankfurt region)
- **Deploy target (later):** Vercel

## Data model

Full schema in [`supabase/migrations/20260717001531_initial_schema.sql`](supabase/migrations/20260717001531_initial_schema.sql),
applied to the remote project. Row-Level Security is enabled on every
table; real role-based policies were added in Step 3 part 2 — see
"Access model (RLS)" below.

Tables (15 total — 14 from the initial schema plus `assignment_materials`,
added in Step 4 part 2):

| Group | Tables |
|---|---|
| People & courses | `profiles` (links to `auth.users`, role enum student/teacher/admin), `courses` (level enum A1–C1), `classes` (course + teacher + dates), `enrollments` (student ↔ class, unique per pair) |
| Coursework | `assignments` (+ `assignment_materials` for teacher-attached files, Step 4 part 2), `submissions` (one per student+assignment; `file_path`/`file_name` for an attached file, renamed from `file_url` in Step 4 part 2), `grades` (one per submission) |
| Attendance | `class_sessions`, `attendance` (status enum present/absent/late/excused, one per student+session) |
| Exams | `question_bank` (type enum multiple_choice/true_false/short_answer/writing/listening/speaking; `media_path`/`media_type` for an attached audio clip or image, added in Step 5 part 1), `exams`, `exam_questions` (join table, ordered), `exam_attempts` (retakes allowed), `answers` (one per attempt+question) |

Design conventions used throughout — worth knowing before extending the
schema later:
- `created_at timestamptz default now()` added to every table as a
  standard audit column, even where not explicitly spec'd.
- `ON DELETE CASCADE` for parent→child ownership (e.g. deleting a class
  deletes its enrollments/assignments/sessions) and for a student's own
  records tied to their `profiles.id`.
- `ON DELETE SET NULL` for "who did this" attribution columns
  (`created_by`, `graded_by`, `teacher_id`) — removing a staff account
  keeps the record but drops attribution.
- `answers.question_id` is the one exception: `ON DELETE RESTRICT`. Once a
  question has real answers against it, it can't be deleted from
  `question_bank` — protects exam history from silently disappearing.
  Unused questions can still be deleted freely.
- All FK columns are indexed; junction/one-per-pair tables have explicit
  `unique` constraints (e.g. `enrollments(class_id, student_id)`).

## Authentication

Email + password auth via Supabase Auth, cookie-based sessions via
`@supabase/ssr` (works across Server Components and middleware, unlike
plain `@supabase/supabase-js` which only does browser localStorage
sessions).

- **Pages**: `/signup` (full name, email, password), `/login` (email,
  password), `/dashboard` (protected — shows the signed-in user's name
  and role). Each has a `page.tsx` (Client Component, for the
  `useActionState` hook that shows inline errors) and an `actions.ts`
  (Server Action doing the actual Supabase call).
- **Logout**: `apps/web/src/components/logout-button.tsx` — a plain
  `<form action={logout}>` with no client JS at all; `logout` is the
  Server Action in `apps/web/src/app/dashboard/actions.ts`.
- **Middleware** (`apps/web/src/middleware.ts` +
  `lib/supabase/middleware.ts`) runs on every request (except static
  assets): refreshes the session cookie (access tokens are short-lived)
  and redirects signed-out visitors away from `/dashboard` to `/login`.
  The dashboard page *also* checks `getUser()` itself and redirects if
  needed — defense-in-depth in case the middleware matcher ever changes.
- Auth checks use `supabase.auth.getUser()`, not `getSession()` —
  `getUser()` revalidates the token against Supabase's Auth server rather
  than just trusting whatever's in the cookie.
- Email confirmation **is required** on this Supabase project
  (`mailer_autoconfirm: false`) — after signup, `signUp()` returns no
  session until the user clicks the confirmation link in their email.
  The signup action handles both cases: redirects straight to
  `/dashboard` if a session comes back immediately, otherwise shows
  "check your email".

### Default-to-student rule (security-critical)

New profiles are created by a **database trigger**
(`supabase/migrations/20260717004354_create_profile_on_signup.sql`) on
`auth.users` insert — not by any application code path. The trigger:

- Hardcodes `role = 'student'` as a literal in the SQL. It is never read
  from `raw_user_meta_data` or anything else client-supplied — the
  signup form only ever sends `full_name` as metadata.
- Runs as `SECURITY DEFINER` (with `search_path` pinned to `public`), so
  it bypasses `profiles`' RLS to perform the insert, since RLS still has
  zero policies at this point.
- There is currently **no way for a user to change their own role** —
  no UI, no API route, nothing writes to `profiles.role` except this
  trigger at creation time. Keep it that way until there's a deliberate,
  admin-only path for role changes.

Verified end-to-end with a throwaway test account created via the Admin
API (pre-confirmed to skip needing real inbox access): trigger created
the profile with `role: "student"` correctly, login → dashboard → logout
all worked, and deleting the test auth user cascade-deleted its profile
row. Test account was deleted after verification.

The dashboard now reads `profiles` via the regular signed-in client (not
the admin client) — switched over in Step 4 part 1, since Step 3 part 2's
"read own profile" policy makes that safe.

## Access model (RLS)

Policies in [`supabase/migrations/20260717015807_add_rls_policies.sql`](supabase/migrations/20260717015807_add_rls_policies.sql),
plus a bootstrap fix in [`supabase/migrations/20260717020436_allow_admin_bootstrap.sql`](supabase/migrations/20260717020436_allow_admin_bootstrap.sql).

### Helper functions (SECURITY DEFINER)

- `is_admin()`, `is_teacher()` — check the caller's own `profiles.role`.
- `teaches_class(cid)` — true if `classes.teacher_id` = the caller, for a
  given class id.
- `is_enrolled(cid)` — true if an `enrollments` row exists for the
  caller + a given class id.

All four are `SECURITY DEFINER`, so their internal queries bypass RLS.
That's required, not just convenient: a policy on `profiles` that calls a
function which queries `profiles` would otherwise re-trigger the same
policy it's in the middle of evaluating (infinite recursion).

### Per-table summary

- **profiles**: SELECT own row, admin sees all, a teacher sees their own
  row plus students enrolled in their classes. UPDATE own row, or (admin)
  any row. No insert/delete policy at all — rows are only ever created by
  the Step 3 part 1 signup trigger.
- **courses**: SELECT any authenticated user; write = admin only.
- **classes**: SELECT admin / own-teacher / enrolled-student; write =
  admin, UPDATE also allowed for the class's own teacher.
- **enrollments, assignments, class_sessions**: same three-way pattern —
  admin / `teaches_class` / `is_enrolled` for read, admin / `teaches_class`
  for write.
- **submissions**: only the owning, enrolled student can insert/update
  their own row. Deliberately no teacher/admin write policy — grading
  happens through the separate `grades` table, not by editing the
  submission itself. No delete policy for anyone.
- **grades** (the critical one): only a teacher of the class, or an
  admin, can insert/update/delete. There is no student write policy
  anywhere — students can only ever `SELECT` their own grade.
- **attendance**: same shape as grades — teacher/admin write only,
  student read-only for their own record.
- **question_bank, exams, exam_questions, exam_attempts, answers**:
  `for all` staff-only policies (`is_admin() or is_teacher()`). Students
  get **zero** access, intentionally and temporarily — safe student-facing
  exam access (seeing exam questions without `correct_answer`, seeing only
  their own attempt/answers) needs its own careful design and is deferred
  to a later step.

### `profiles.role` protection + the bootstrap fix

Same trigger from Step 3 part 1 (blocks changing `role` unless
`is_admin()`), refined here after testing surfaced a bootstrapping
problem: the trigger blocked even the **service_role key** from setting
the very first admin, since `is_admin()` depends on `auth.uid()`, which is
`NULL` for non-user contexts (service_role, direct SQL in the Dashboard).
Fixed by allowing the role column to change when `auth.uid() is null` —
relevant only to trusted server-side access that already fully bypasses
RLS anyway. An ordinary signed-in user, including a teacher, still can
never change any role, their own or anyone else's.

### Verified

26 real access-pattern checks against the live project, using 5
disposable test accounts (1 admin, 2 teachers, 2 students — created and
fully deleted afterward via the Admin API) plus temporary test data
(course/classes/enrollments/assignment/submission/grade/session, also
cleaned up). Covered: profile visibility scoping, role-change protection,
cross-teacher and cross-student isolation on classes/assignments, the
submission ownership+enrollment checks, the grades
students-can-never-write rule, attendance write restrictions, and
exam-table staff-only access.

One methodology note worth remembering for future testing: an `UPDATE`
whose `WHERE` doesn't match any RLS-visible row succeeds with **zero rows
affected** — it does not raise an error. Testing "this write should be
blocked" by checking for an error is wrong for UPDATE/DELETE; check the
actual stored value (or the returned row count) instead. (INSERT is
different — a `WITH CHECK` violation on insert does raise a real error.)

## Classroom features (assignment loop, Step 4)

### Routes

- `/dashboard` — role-aware. The query is identical for every role
  (`select * from classes`); RLS alone decides what comes back (a
  teacher's own classes, a student's enrolled classes, or every class for
  an admin). Only the heading text varies ("Classes I teach" / "My
  classes" / "All classes"). Admin gets this same unified list rather
  than separate empty "teacher"/"student" sections, since an admin
  account isn't naturally a teacher or an enrolled student — a real
  admin panel is still deferred.
- `/classes/[classId]` — the class page. Fetches the class and its
  assignments through the regular signed-in client; RLS decides
  visibility (404-style "not found" message if the caller can't see it,
  rather than an error). Whether the viewer sees the teacher's "New
  assignment" form or the student's per-assignment submission-status
  badges is decided by `class.teacher_id === user.id || role === 'admin'`
  — not a hard-coded role switch, so an admin gets the same write access
  the RLS policies already grant them.
- `/classes/[classId]/assignments/[assignmentId]` — same page, two
  render paths: staff see the submissions list (student name + graded/
  needs-grading badge, linking to the grading page); students see the
  instructions plus either a submit form or (once submitted) their own
  content and, once graded, their points + feedback.
- `/classes/[classId]/assignments/[assignmentId]/submissions/[submissionId]`
  — the grading page. Staff-only; if a student reaches this URL for
  their own submission it redirects them back to the assignment page
  (which already shows the same info read-only) rather than showing a
  form they have no RLS permission to submit.

### Assignment loop

1. Teacher creates an assignment on the class page (title, instructions,
   due date, max points) → `assignments` insert, gated by
   `assignments_insert` (admin or `teaches_class`).
2. Student opens the assignment, submits a text answer → `submissions`
   insert with `student_id` always set from the verified session, never
   from form input. Gated by `submissions_insert_own` (own id + enrolled
   in that class).
3. Teacher opens the submission, enters points + feedback → the action
   checks whether a `grades` row already exists for that
   `submission_id` and inserts or updates accordingly (`submission_id`
   is unique, so it's one or the other, never both). Gated by
   `grades_insert`/`grades_update` (teacher of the class, or admin).
4. Student reopens the assignment and sees their points + feedback,
   read straight off the same query — no separate "check for grade" step.

None of the pages re-check "is this person allowed to do this" in
application code beyond deciding which UI to render — every actual read
or write goes through the regular signed-in Supabase client and lives or
dies by the Step 3 part 2 RLS policies.

### File handling (Step 4 part 2)

Two private Supabase Storage buckets (created manually in the Dashboard,
not via migration): `submissions` and `materials`. **Neither is ever
exposed via a public URL** — every view/download goes through a
short-lived (5 minute) signed URL generated server-side by
[`apps/web/src/lib/supabase/signed-url.ts`](apps/web/src/lib/supabase/signed-url.ts),
using the regular signed-in client so `createSignedUrl` itself is gated
by the same bucket RLS policies below (it fails if the caller can't
`SELECT` that object). Allowed types (pdf, doc/docx, common images,
mp3/m4a/wav) and the 20MB cap live in
[`apps/web/src/lib/files/constants.ts`](apps/web/src/lib/files/constants.ts),
checked both client-side (fast feedback) and server-side in the Server
Actions (the real boundary).

- **`submissions` bucket** — a student's own attached file, one per
  submission. Path: `{class_id}/{assignment_id}/{student_id}/{filename}`.
  Private to: the owning student (read/write), the class's teacher
  (read-only), admins (read-only). Not even a teacher/admin can
  upload/replace here - matches how the `submissions` table itself only
  ever allows the owning student to write. `submissions.file_path` (renamed
  from `file_url` - it's a private Storage path, never a URL) and the new
  `submissions.file_name` column store what's attached. Replacing a file
  (allowed until graded) deletes the old Storage object first so nothing
  is orphaned.
- **`materials` bucket** — many teacher-attached files per assignment,
  tracked in the new `assignment_materials` table (`assignment_id,
  storage_path, file_name, file_type, uploaded_by, created_at`, `storage_path`
  unique). Path: `{class_id}/{assignment_id}/{filename}`, with a random
  8-char prefix on the filename (multiple materials can share an original
  name). Write (upload/delete) is staff-only (teacher of that assignment's
  class, or admin); read is staff + any enrolled student. Removing a
  material deletes both the Storage object and its DB row.

Both buckets' policies are on `storage.objects` (private per Supabase
project by default, RLS already enabled) using
`storage.foldername(name)` to read the path segments - e.g.
`(storage.foldername(name))[1]` is `class_id` for both buckets,
`[3]` is `student_id` for submissions. They reuse the exact same
`is_admin()`/`teaches_class()`/`is_enrolled()` helpers from Step 3 part 2 -
no new helper functions needed, since `storage.objects` is just another
RLS-protected table. Migrations:
[`20260717114246_add_file_handling_schema.sql`](supabase/migrations/20260717114246_add_file_handling_schema.sql)
(table changes) and
[`20260717114317_add_storage_policies.sql`](supabase/migrations/20260717114317_add_storage_policies.sql)
(bucket policies).

Verified with 11 scripted storage-RLS checks (own-folder upload, cross-student
and outsider isolation on both buckets, teacher-cannot-write-submissions,
student-cannot-write-materials) plus a full real-UI pass: upload, download
(confirmed the signed URL actually serves the right bytes), replace
(confirmed the old object is deleted, not orphaned), grading with a file
attached, and the edit form correctly disappearing once graded. All test
accounts/data/files were created and fully removed afterward - a real
`<input type="file">` can't be driven by a script (browsers block setting
`.files` for security), so the UI pass used the browser's `DataTransfer`
API to construct a `File` object and assign it directly, the same trick
real E2E test frameworks (Playwright/Cypress) use for this.

### Seed data

[`supabase/seed.sql`](supabase/seed.sql) finds a teacher and a student by

### A gotcha worth remembering: PostgREST embeds are objects, not arrays, for to-one relations

When embedding a related table through a foreign key that's `unique`
(e.g. `submissions` embedding `grades`, since `grades.submission_id` is
unique), PostgREST/supabase-js returns a single object (or `null`), not
an array. Code here originally assumed an array everywhere (`grades?.[0]`)
copying the pattern used for to-many relations — it silently evaluated to
`undefined` instead of erroring, so the bug only showed up as "the grade
saved to the database correctly but the UI wouldn't show it." Fixed by
typing these as a single nullable object. Worth checking the actual
shape of a nested select's response rather than assuming, especially
across a unique FK.

## Exam authoring (Step 5 part 1 — staff only, no student access yet)

Question bank and exam builder for teachers/admins. Students get **zero**
access anywhere in this part — no new table-level RLS policies were
needed at all; it entirely reuses the staff-only `for all` policies on
`question_bank`/`exams`/`exam_questions` from Step 3 part 2. The only new
access-control surface is the `exam-media` storage bucket (see below).

### Routes

- `/exams/questions` — question bank list, filterable by level and type
  via a plain GET form (no client JS - the URL's query string *is* the
  filter state). Each row can be edited or deleted.
- `/exams/questions/new` and `/exams/questions/[questionId]` — a shared
  `QuestionForm` client component handles both create and edit. The
  `type` field is controlled, so picking multiple_choice/true_false/
  short_answer/writing/speaking swaps in the right fields live.
- `/exams` — exam list + a "New exam" form (title, level, duration,
  optional class, certification checkbox).
- `/exams/[examId]` — the exam builder: shows total points and question
  count computed from `points_override ?? question.points`, lets staff
  add questions from the bank (same level/type filter, hides
  already-added questions), reorder with ↑/↓, remove, and set a
  per-exam points override.

Every one of these pages calls
[`requireStaff()`](apps/web/src/lib/supabase/require-staff.ts) first,
which redirects non-staff straight to `/dashboard`. RLS alone would
already return empty results to a student, but for a section that's
*entirely* staff-facing (unlike classes/assignments, which serve both
roles), an explicit redirect is clearer than a confusing empty page.

### Auto-graded vs manual-graded question types

- **Auto-graded** (`multiple_choice`, `true_false`, `short_answer`):
  store a `correct_answer`. For multiple choice, `options` is a JSON
  array of strings and `correct_answer` is the exact text of the correct
  one (chosen via a radio button keyed by index while authoring, to
  avoid ambiguity if two options happen to share text).
- **Manual-graded** (`writing`, `speaking`): `correct_answer` and
  `options` are always `null` - a teacher reads/listens and scores these
  later (part 2+). The Server Actions null these out server-side
  regardless of what a request contains, not just hide the fields in the
  UI.

**"Listening" is deliberately not a selectable type.** The
`question_type` enum has a `listening` value from the original schema,
but this app treats listening as an *attribute* - any of the 5 real
types can optionally have an audio clip attached, and that's what makes
it a listening question. The type dropdown only ever offers the 5 real
types; `listening` as an enum value is simply unused by this UI.

### exam-media bucket

Private Storage bucket (created manually, like `submissions`/
`materials`) for a question's optional single audio clip or image.
Path: `{question_id}/{filename}`. Staff-only for every operation (read
*and* write) via one `for all` policy reusing `is_admin()`/
`is_teacher()` - simpler than the Step 4 buckets since there's no
per-class path segment to parse, and no student read access at all yet
(that's scoped, careful work for part 2 - a student should see the
media for a question they're actively attempting, nothing else).
`question_bank.media_path` + `.media_type` store what's attached;
replacing or removing media deletes the old Storage object. Migration:
[`20260717132801_add_exam_media.sql`](supabase/migrations/20260717132801_add_exam_media.sql).
